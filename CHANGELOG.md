# Changelog

## Unreleased

### Breaking

- A build is its store and its id in the store, so a Google Play build and an App Store build (or an Amazon, Huawei, Samsung build) may share a package name / bundle id. `game_app` gets `store_app_id` (the id in the store: package, bundle id, Steam App ID, any id of a web build) and its key `app_id` becomes `{store}:{store_app_id}` (`google:com.example.mygame`, `apple:com.example.mygame`); products, ledger rows, secrets scopes, integrations, revenue rows and every admin call use the key. Store API calls, notification URLs (`/notify/amazon?app=<package>`, ...), the game's `BillingEvent.app_id` and integration events carry the id in the store. The `.amazon` / `.huawei` / `.samsung` / `.quest` suffixes are no longer needed, and the `samsung_package_name` secret is gone (the build's id is the package).
- Client requests name the build by its id in the store and its store: routes whose path names no store (`/entitlements`, `/restore`, `/paywall`, `/paywall/event`, `/attributes`, `/redeem`, `/wallet`, `/wallet/spend`) and the game-backend routes `/server/*` take `store`; the SDKs send it (Unity from its store adapter, TypeScript `store`, Godot and Defold a `store` setting). Older clients are refused with `400 [ERR_BAD_REQUEST] store is required`.
- `admin_upsert_game_app` takes `store_app_id` instead of `app_id`; seed files (`apps.json`: `store_app_id`; the other files: build keys), `bulk_setup.py` (`store_app_id` column, product rows by key), `setup_google.py --package`, `import_revenuecat.py` (`--app apple=<bundle id>` → `apple:<bundle id>`) follow.
- Needs a publish with `--delete-data`: the builds' keys change. Load the setup again with `seed.py` (or the admin page) afterwards.

### Added

- Exchange rates for the currencies the ECB does not publish (UAH, VND, KZT, ...): the market rates of the open `fawazahmed0/currency-api` (jsDelivr, its `currency-api.pages.dev` mirror next; no key), fetched with the ECB's every 6 hours and backfilled a day per file back to the first sale (history from 2024-03-02). The ECB stays the source of its own currencies and a manual rate wins over both. New table `fx_market_day` (migrates in place); the report's `by_currency` rows say where each rate comes from (`rate_source`: `ecb`, `market`, `manual`, `telegram`), shown on Revenue → By currency, and `fx.market_as_of` gives the latest market day.
- A store catalog import maps every store id to a product of the app (a **→ Product** column): the build's own product, else the id without the bundle in front and a store suffix (`com.example.game.coins_700.ios` → `coins_700`), editable or picked from the app's products. A store id under a product of another build joins it (its id in this store), and two store ids under one product, or a product this build already has under another id, are refused before saving.
- App Store builds can have their own title and description (the App Store takes 35 and 55 characters, Google Play 55 and 200): the product dialog has App Store fields (empty: the shared ones) and character counts against each store's limit; Create in store sends each store its own text and shows the counts before the check; a catalog import fills each build's own listing, and a new row of another store only with what fits there.
- The catalog import brings the store listing (title and description, in English when the store has one) of Google Play and App Store products, and the App Store's prices (the US price, else the base territory's): a call or two per App Store product. The listing fills only fields that are empty here.
- The Setup tab asks Apple for a test notification from each App Store build's card (**Test notification**, next to Set in App Store Connect) instead of one button for every App Store build.
- The Products tab is a sortable grid with hideable columns, a search (product id, store ids, title), type and "missing in <build>" filters, and bulk actions on the checked rows: change the type, add to or remove from a build, create in the store, delete. The product dialog has **Delete** too (the product goes from every build; purchases of it stay in the ledger). `RichTable` takes an optional row selection.
- The Add an app wizard asks for the app's name first and derives the app key from it (`Magnet Rings` → `magnet-rings`) until the key is typed; the name is saved with the builds (`admin_set_app_name`). A name with no Latin letters leaves the key to the app id, as before.

### Changed

- A catalog import from Google Play (which does not say whether a one-time product is used up) suggests `non_consumable` for new one-time products whose id names a lasting unlock (`no_ads`, `remove_ads`, `premium`, `unlock`, `lifetime`, `vip`, ...) and `consumable` for the rest, marks the guess **check**, and a store id that joins an existing product takes that product's kind. `admin_list_store_products` rows carry `kind_known`.
- GA4 events can carry the player: `send_user_id` (**Send the player's user id as GA4 user_id**, off by default) sends the billing user id as GA4's `user_id`, for games that give Firebase the same id; and a purchase lands in the session it was made in when the client sends `attribution.ga_session_id` (Firebase's session id). Session ids are kept only from the latest request and used within 30 minutes of it (`session_at_ms`, set by the server), so refunds and renewals do not reopen an old session.
- Amplitude events land in the player's session when the client sends `attribution.amplitude_session_id` (the SDK's session id, used within 5 minutes), and Mixpanel events go to the player Mixpanel already knows when it sends `attribution.mixpanel_distinct_id` (the SDK's `distinct_id`, `$device:...` allowed; the billing id then goes as `purser_user_id`).
- The admin page names a build by its store ("Google Play", "App Store", "Steam"), with the platform only for a store of several platforms ("Xsolla (Android)"), instead of "Android · Google Play"; the import menu says "From Google Play".

### Fixed

- The setup check said when refunds were last read as "read 0 h ago": it says "just now", minutes, hours or days now.
- An App Store build whose app is not on the App Store yet failed with "App Store rejected the API key (HTTP 401)": Apple refuses production requests for such an app with 401, not 404, and Purser took the refusal for a wrong key without asking the sandbox. A transaction look-up, the refund sweep and the setup check go on to the other environment; the key is reported wrong only when both refuse it.
- A store catalog import with "Also add to" other builds overwrote their products: an App Store import (which carries no prices) set the Google Play prices to 0. The other builds now get only the products they do not have, and a store that reports no price keeps the price a product has. "Also add to" starts unchecked.
- The Apple keys are labelled by where they come from: the In-App Purchase key (Users and Access > Integrations > In-App Purchase) checks purchases, the Team key (App Store Connect API > Team Keys) imports the catalog and sets up the App Store.
- The refund sweep of Google Play builds read voided purchases from exactly 30 days back, which Google refuses ("Start time must be within [30] days of data"): it starts a day later now, so refunds no notification reported are found again.
- Set up with Google Cloud: a push subscription refused with `iam.serviceAccounts.actAs` says which service account it authenticates as (the build key's, possibly of another project) and that the token's account needs Service Account User; the role is in the list of needed roles too (docs/store-setup.md).
- Importing the catalog of a Google Play app without subscriptions (or one-time products) failed with `bad subscriptions response: EOF`: Google answers an empty list with an empty body. The refund sweep read an empty voided-purchases answer the same way.

## 0.14.0 - 2026-11-27

**In short:** Google Play notifications are authenticated by Pub/Sub's push token instead of a secret in the URL; integrations take the game's own event names and name free trials and subscription refunds apart, and GA4 counts renewals as purchases; releases carry a signed build provenance, and every page of the docs is rewritten for reading.

**Upgrade:** in place over 0.13.0 (one new table): no `--delete-data`, no backup needed. Google Play builds set up before need their push subscriptions changed (Breaking, below): until then their notifications are refused.

### Breaking

- Google Play notifications are authenticated by Pub/Sub's push token instead of a secret in the URL (a query string ends up in logs): the push subscription sends an OIDC token of the build's service account with the audience `purser-rtdn:<app_id>`, and the server checks it against Google's published keys (cached in the new table `google_cert`, fetched again for an unknown key at most once a minute). The push URL is `/notify/google` without `?secret=`, and `google_rtdn_secret` is gone. A Google Play build set up before needs its push subscription changed: run the Google Cloud setup again (Setup tab, or `setup_google.py`), or turn on authentication in the subscription by hand (docs/store-setup.md). The module publishes in place: no `--delete-data`.

### Added

- Releases carry a signed build provenance attestation of `purser.wasm` and `seed.example.zip`: `gh attestation verify purser.wasm -R yevhenii-sir/purser` checks that the file was built by the release workflow from the tagged commit (README, docs/getting-started.md).
- CI runs the Godot addon's tests on Godot 4.2, the oldest supported version.
- docs/releases.md, *Versions and upgrades*: Purser has not run a live game yet, how far each store has been tried (automated tests, sandbox and live purchases), what a release promises before and after 1.0, how often releases come out and how to upgrade. The README and the docs site's front page say the status.
- GitHub releases carry their notes from the changelogs (`tools/release_notes.py`: the release's section of `CHANGELOG.md` and of the Unity package's), and a tag without a changelog section publishes nothing. Every released section starts with **In short** and **Upgrade** lines, added to the earlier releases too.
- README: *Performance*, the measured answers per second and what limits them.
- Integrations take the game's own event names: `event_names` in GA4, Amplitude, Mixpanel, Braze (custom events) and OneSignal, next to AppsFlyer, Singular and Kochava; a name turns on an event the integration does not send by default, an empty one turns it off. Narrow keys name some of a kind's events apart: free trials (`trial_start`, `trial_converted`, `trial_cancel`, `trial_uncancel`, `trial_expire`) and refunds of subscriptions (`subscription_refund`); one without a name takes its kind's, and Adjust's `event_tokens` take them too. The admin page edits them in an **Event names** section of the integration, a switch and a name per event (switching on an event that is off by default fills in a ready name); for these integrations the switches replace the **Events** checkboxes (Braze keeps them for the payments it gets as purchases). The integration dialog is wider and split into **Connection** and **Events** tabs, with the **Enabled** switch next to its title; the **Events** checkboxes of the other integrations are grouped into payments and subscription changes, start checked (unchecked: not sent) and list only the events the integration sends (Adjust has none: its event tokens choose; Tenjin's `expire` is its `send_expire`); it has **Copy settings from**: the names and options of the same integration on another build of the app, without that build's app ids and key. Every integration event carries `trial` and `trial_conversion` (webhook and storage exports, Braze and OneSignal properties; `docs/bigquery-schema.json`).
- AppMetrica gets free trials as `trial_started`, the first payment after one as `subscription_converted`, and cancellations, re-enabled renewals and billing issues as `cancellation`, `uncancellation`, `billing_issues`.

### Changed

- GA4 gets renewals and the first payment after a free trial as `purchase` (was `subscription_renew`): GA4 counts revenue only of its e-commerce events, so renewals were missing from its revenue. A free trial is `trial_started` instead of a `purchase` of value 0, and the subscription changes (cancellations, billing issues, pauses, ...) go out when named in `event_names`.
- SECURITY.md: what anyone who knows a player id can read without player tokens, and turning them on instead of relying on ids nobody can guess.
- Docs: the README and the docs site's front page list every implemented store (Huawei AppGallery, Samsung Galaxy Store, Meta Quest and Telegram Stars were missing) and the SDKs for other engines.
- The module's tests are split by area (`server/spacetimedb/src/tests/`: the harness in `mod.rs`, one `<area>_tests.rs` per area) instead of one file of 10,800 lines.
- Docs: every page rewritten for reading, with the same facts: an opening that says what the page is for, numbered steps, tables for options and cases, warnings for what loses data or money, shorter sentences. The docs site's sidebar groups the pages (Get started, Stores, Your game, Selling, Revenue and alerts, Running the server, Migrating, Reference) and shows the open page's sections as a tree, with breadcrumbs above the page.
- CONTRIBUTING.md: `main` stays linear; work from side branches and agents' worktrees lands as rebased or squashed commits.

## 0.13.0 - 2026-11-26

**In short:** Moving to another server without losing a purchase (`migrate.py --switch`); admins sign in with Google, GitHub or Discord through an OpenID Connect provider, invited by email or by company domain; the admin page shows each role only what it can do.

**Upgrade:** in place over 0.12.0 (new tables only): no `--delete-data`, no backup needed.

### Added

- Moving to another server without losing a purchase (`docs/moving-servers.md`). `migrate.py --switch` pauses the old server (every client, server-key and store route answers `503` + `Retry-After`, its worker, deliveries, integration events and alerts wait), copies the database, marks the new one as moved in and then forwards every route of the old server to the new one, body and headers as they were, until nothing reaches it. The old server's Server page counts what still arrives per route and build; the new one lists per build whether purchases and store notifications reach it yet and what else points back (provider sign-in, inter-database delivery, admins with tokens); every page of a moving server says so. `/healthz` reports `moving`. Owner procedures `admin_set_move`, `admin_mark_moved_in`, `admin_move_checklist`; the new table `forwarded_daily` migrates in place.
- Docs: a stable address of your own in front of the server (Caddy and Cloudflare Worker recipes) so a move needs no new game build and no store console changes, and everything that knows the server's address. The public address setting accepts such an address (`https://billing.example.com`), not only the route base.
- Admins sign in with Google, GitHub, Discord and other accounts through an OpenID Connect provider: SpacetimeAuth on maincloud, any provider on a self-hosted server (docs/self-hosting.md, *Sign-in with Google, GitHub and other accounts*). Admins → *Sign-in with a provider* sets the issuer and client ID (Purser checks the provider's discovery document: exact issuer, PKCE with S256); coworkers are invited by email with a role and apps, and the first sign-in with that verified email within 7 days makes them an admin. They stay bound to the provider and client they joined with: a token another application got from the same provider is refused. Tokens keep working. Domain rules let everyone with a verified email of a company domain in as Viewer or Support, optionally only accounts of the organization (Google Workspace's `hd` claim); public email domains are refused, the docs list the rules of use, removing the rule removes its admins, and someone removed stays out of the rule until invited. New tables `admin_invite`, `admin_sign_in`, `admin_domain_rule` and `admin_domain_block` migrate in place.
- A logo (`docs/images/purser.svg`): the docs site's logo and favicon, the admin page's favicon and its mark in the sidebar.
- Docs: *How it works* (`docs/flows.md`), sequence diagrams of purchases, store notifications, delivery retries, restores on another player, Stripe, Steam and Telegram checkout, analytics events, paywalls and the wallet.

### Changed

- Admin page: every role sees only what it can do. Viewers get no buttons that change anything and read settings as disabled fields; support sees the player actions and manual grants; editors no keys, store setup or account keys; server-wide actions (rates, store fee, revenue rebuild, worker, metrics, delivery hosts) are hidden from admins limited to some apps or, for the hosts, from everyone but the owner. The demo takes `?role=viewer` (or `support`, `editor`, `admin`) to show it.
- Add an app wizard: an editor (no keys capability) sets up the app without keys: the delivery and store key steps say which keys an admin adds on the Keys tab instead of asking for them.
- Admins page: the admin list is a sortable grid with a search (name, email, identity, apps) and a role filter (one of them: the admins of domain rules); an admin's apps show as a control like the role (the first app and how many more, all of them in its tooltip); picking apps (admins, invitations, domain rules, alert channels) names the chosen ones above the list, lists them first and ticks everything a filter matches at once; lists of apps in tables take one line; *Needs attention* on the Overview pages through every problem with a filter instead of showing 12; changing the role or apps of an admin who joined through a domain rule asks first, since it detaches them from the rule.

## 0.12.0 - 2026-11-26

**In short:** Samsung Galaxy Store and Meta Quest; virtual currency wallets; paywall audiences and install cohorts; Google Play subscription add-ons and price changes of subscriptions; Singular, Branch, Kochava, Braze and OneSignal integrations and an S3-compatible export; client SDKs for TypeScript, Godot and Defold.

**Upgrade:** publish with `--delete-data` and keep the data with `backup.py` (see Breaking).

### Breaking

- Publish with `--delete-data` (keep the data with `backup.py`): `purchase` gains `price_change` and `price_change_micros`, `placement` gains `audiences_json`, `product` gains `wallet`, `revenue_report_job` gains `subs_next_ms` and `subs_json` (not backed up: reports are counted again). The new `running_subscription` is derived from the ledger: the restore's reindex fills it.

### Added

- Large ledgers: the subscriptions running now are counted a batch per scheduled call, in windows of when their access ends, from a new in-memory table of the paid subscriptions players own (`running_subscription`, kept in step with the ledger like `owned_purchase`, with what is counted: no step reads the ledger) (`subs_count.rs`): the daily snapshot (`subscription_daily`) is a walk of its own (new tables `subscription_snapshot_job`, `subscription_snapshot_tick`), and the full report counts `active_now`, MRR and the renewal states in a phase of its background job. Both read every subscription players own in one call until now (~0.3 s of native code at 100,000 purchases, growing with the subscribers).
- Google Play subscription add-ons: the other line items of a subscription purchase (products bought and billed with it) are recorded as subscriptions of their own (ledger id `google:{order}+{product}`, token `{token}#{product}`): granted to the purchase's owner, counted in revenue and `/entitlements`, renewed and ended with the purchase, and ended alone when the player removes one. Only the first line item was recorded until now. The subscription is the purchase's first line item.
- Price changes of subscriptions: a price increase announced by Google Play (`priceChangeDetails`) or the App Store (`priceIncreaseStatus`, `renewalPrice`) is kept on the purchase (`price_change`: `consent_needed`, `accepted`, `scheduled`; `price_change_micros`). The purchase page shows it, the purchase list filters the subscriptions whose player has not accepted an increase (they end with their period unless the player does), and the full report counts them (`price_consent_needed_now`, on the Revenue page). `purchase` gains `price_change` and `price_change_micros`.
- Audiences of a placement (docs/paywalls.md "Audiences"): groups of players who get their own paywall instead of the variants and the A/B test, by the build's platform, the client's app version, days since the player was first seen, a running subscription, products owned and player attributes (`/attributes`: country, spender segment, ...). The first matching audience wins; its paywall is served and counted as variant `audience.{id}`. Edited in the placement dialog of the Paywalls tab. `placement` gains `audiences_json`.
- Install cohorts in the full revenue report and on the Revenue page: players by the month the server first heard from them, with how many paid and their cumulative net revenue per installed player by month since the install (docs/analytics.md). New table `install_daily` (new players per build and day, counted from this version on): publish in place.
- Virtual currency wallets (docs/wallet.md): a product's `wallet` (`gems:100`, per unit) credits the player's balance when the purchase is granted and takes it back when it is refunded or revoked (the balance may go below zero), again when it is reinstated. The game reads and spends balances with `/wallet` and `/wallet/spend` (builds with player tokens) or from its backend with `/server/wallet`, `/server/wallet/grant`, `/server/wallet/spend` (server key scope `wallet`); every change has a reference and is applied once. The player page shows balances and history and adjusts them (Support); exports and erasures include the wallet. New tables `wallet_balance`, `wallet_tx`; `product` gains `wallet`.
- Samsung Galaxy Store (store `samsung` of `android` builds): `/verify/samsung` checks one-time products with Samsung's receipt API (by `purchaseId`) and subscriptions with the Galaxy Store Developer API (service account: `samsung_service_account_id`, `samsung_private_key`); after the grant the server consumes consumables and acknowledges subscriptions. Instant Server Notifications (`/notify/samsung?app=…`, a JWT verified with `samsung_iap_public_key`) look the purchase up again; subscriptions are re-checked when their period ends. `samsung_package_name` names the package when the app id is not it. The price paid and the buyer's country come from Samsung. No schema change.
- Imported purchases of the last 62 days count in the builds' sales (`build_sales_daily`), so business alerts work right after moving from another backend (`admin_import_purchases`, `import_revenuecat.py`) instead of a week later.
- S3-compatible export (`s3`): every event as the same NDJSON object as the Cloud Storage export, uploaded with a path-style `PUT` to AWS S3, Cloudflare R2, MinIO or any S3-compatible endpoint (`endpoint`, `region`, `bucket`, `prefix`; secret `s3_access_key` = `ACCESS_KEY_ID:SECRET_ACCESS_KEY`), signed with AWS Signature V4 (`purser_core::sigv4`, checked against AWS's published test suite).
- Singular integration (`singular`, S2S EVENT endpoint, `singular_sdk_key`): revenue events with the Singular SDK's device id (`sdid`, V2) or the device ids (V1), refunds with a negative amount, cancellations as `subscription_cancelled`; `event_names` renames them. New attribution keys `singular_device_id` and `app_set_id`.
- Branch integration (`branch`, v2 Event API, `branch_key`): purchases, renewals and paid subscription starts as `PURCHASE` with revenue, free trials as `START_TRIAL`, refunds and expirations as custom events.
- Kochava integration (`kochava`, server-to-server events, `kochava_app_guid`): events with the revenue in `sum`, matched by the new attribution key `kochava_device_id` or the device ids.
- Braze integration (`braze`, `/users/track`, `braze_rest_api_key`): purchases (refunds with a negative price) and `purser_<kind>` custom events, subscription changes included, for `external_id` = the billing user id.
- OneSignal integration (`onesignal`, Custom Events API, `onesignal_api_key`): every event as a `purser_<kind>` custom event for `external_id` = the billing user id, with an idempotency key.
- Integrations that answer 2xx and name refused events in the body (Singular, Braze, OneSignal) count those events as failed instead of sent.
- Meta Horizon Store (Meta Quest; store `meta` of `android` builds): `/verify/meta` checks the player's user proof (`store_user_proof`, a nonce from `Users.GetUserProof`, with the Meta user id as `store_user_id`) with `user_nonce_validate`, then looks add-ons up in `viewer_purchases` and subscriptions in `application/subscriptions` with the app access token (`meta_app_id`, `meta_app_secret`). The server consumes consumables after the grant (`consume_entitlement`); Meta sends no notifications, so subscriptions are re-checked when their period ends. `/restore` takes one `store_user_proof` for all its items. The setup check lists the app's add-ons with the token.
- Unity: `MetaQuestStoreAdapter` with its bridge (sample "Meta Quest").
- Client SDKs for other engines (docs/sdks.md): `@purser/client` for TypeScript (`sdks/typescript`: web games, Cocos Creator, PlayCanvas, Telegram Mini Apps; `fetch`, no dependencies; Stripe and Telegram Stars checkout helpers, signed answers checked with Web Crypto), a Godot 4 addon (`sdks/godot`, `HTTPRequest`) and a Defold module (`sdks/defold`, `http.request`, a library dependency). Each covers `/verify/<store>`, `/restore`, `/entitlements`, `/paywall`, `/paywall/event`, `/attributes`, `/redeem`, `/wallet`, `/wallet/spend`, player tokens refreshed after `401 ERR_CLIENT_AUTH`, retries of transport errors, 5xx and 429 (`Retry-After`) but never other 4xx, and the Unity package's rules for finishing store purchases. What each sends is kept in `server/spacetimedb/sdk-requests/` (`typescript.json`, `godot.json`, `defold.json`); the module's tests parse every body, refuse fields the server does not read and replay the purchase flow.
- Unity: Google Play subscription offers chosen by the game (`GetGoogleOffersAsync`, `PurchaseOptions.GoogleOfferToken`)
  through an Android plugin of the package, next to Unity IAP 5, which buys only the first offer of a product. The
  purchase reaches `/verify/google` like any other, with its `offer_id`; the server acknowledges it. No server change.

### Changed

- Overview: a **Needs attention** list of open owner alerts and builds whose setup check warns or fails (a click opens the Alerts page or the build's Setup tab); a waiting purchase's error is a line under its id, the whole text on hover, instead of a column cut off at the table's edge.
- The purchase panel is twice as wide (it stayed at the side sheet's narrow default), so its details and history read without breaking every id.

## 0.11.0 - 2026-11-26

**In short:** Huawei AppGallery and Telegram Stars; promo codes and purchases of several units; prices, taxes and refunds read from the stores' APIs; refunds and extensions from the purchase page; business alerts, `GET /metrics` and an `analytics` = `off` mode for large games.

**Upgrade:** publish with `--delete-data` and keep the data with `backup.py` (see Breaking).

### Breaking

- Publish with `--delete-data` (keep the data with `backup.py`): `purchase` gains `quantity`, `tax_micros`, `refund_share_milli`, `reinstated`, `access_was_until_ms` and `error_log_id` (`backup.py restore` gives the restored purchases `quantity` 1, the rest 0). `revenue_report_row` is gone. The business alerts read the new `build_sales_daily`, which starts empty: `revenue_drop`, `refund_spike` and `no_purchases` compare against a week of sales recorded after the upgrade. The delivery event (`BillingEvent`, the webhook body, the `spacetimedb_idc` struct) gains `quantity` after `kind`: game modules add it to their struct (`server/game-receiver`, docs/game-integration.md).

### Added

- Promo codes: an app's codes (admin page → the app → **Promo codes**, `admin_upsert_promo_code`) give a product of its catalog to each player once, without a payment: `POST /redeem` grants it through the ledger like a manual grant (no revenue, the game gets `grant`; a subscription code lasts its days), limited by a number of players and an end date. Unity: `RedeemCodeAsync`, which raises `PurchaseSucceeded` like a purchase. New tables `promo_code`, `promo_redemption`: publish in place. Redemptions are erased and exported with the player's data.
- Purchases of several units at once: a Google Play product with multi-quantity (refused until now) and a StoreKit purchase with a quantity are granted with `quantity` in the game event and the `/verify` answer (Unity: `PurchaseResult.Quantity`); the ledger row keeps it and its price is the unit price × the quantity (App Store transactions report the unit price, although Apple's reference says the total). Integrations get the quantity (GA4 items, AppsFlyer `af_quantity`) and, where they multiply the price by it (Tenjin, AppMetrica, Amplitude), the unit price. A refund of some units of such a purchase is a partial refund (below).
- Unity: `HuaweiStoreAdapter` and `TelegramStoreAdapter` with their bridges (samples "Huawei AppGallery", "Telegram Mini App").
- Huawei AppGallery (platform `huawei`): `/verify/huawei` looks purchases up in the HMS IAP Order and Subscription services with an app-level token (`huawei_client_id`, `huawei_client_secret`, optional `huawei_site`), server notifications (`/notify/huawei?app=…&secret=…`, version 2 or 1) look the purchase up again, subscriptions are re-checked when their period ends. The price paid and the buyer's country come from Huawei.
- Telegram Stars (store `telegram` of `web` builds): `/checkout/telegram` creates an invoice link of the game's bot for a product priced in `XTR`, the bot's webhook (`/notify/telegram?app=…`, set from the Setup tab) answers pre-checkout queries and grants `successful_payment` / revokes `refunded_payment`, `/checkout/telegram/status` answers from the ledger. Subscriptions renew every 30 days; one that is not paid again ends with its period. Stars count as $0.013 in revenue. New table `telegram_order`: publish in place.
- `analytics` = `off` is the mode for large games: only what purchases need is kept, and business alerts (`revenue_drop`, `refund_spike`, `no_purchases`, `notifications_silent`, the daily summary) and the revenue gauges of `/metrics` keep working. They read a new table `build_sales_daily` (production sales per build, day and currency, counted live in every mode and kept 62 days; publish in place) instead of the revenue aggregates. ### Security

- The price and currency a client reports are used only when believable (a three-letter currency with an exchange rate, at most $10,000 and within 20× of the catalog price); revenue sums saturate. A client could write any revenue (and any currency) before. Google promo-code and rewarded purchases count as 0.
- The build-wide limit of `/verify` and `/restore` is spent per store call, after the request was checked (`STORE_CALLS`, 600 a minute): junk requests could use it up and block every purchase of a build. A `/restore` with the same purchase twice looks it up once. `/attributes` and `/paywall/event` have a ceiling per build too. A player is remembered (`player_profile`) only by a request that reaches the store.
- Report ranges with years outside 1900..9999 are refused (the day arithmetic could overflow and loop over billions of days).
- Admins: a build cannot be named `default` or like a developer account (and an account not like a build), which let an admin limited to some apps write shared secrets; such an admin can no longer move a build to an account other apps use. `public_base_url` and the App Store notification setup need the Secrets capability (the URL carries the notification secret). The delivery webhook URL must be a public https address.
- Player tokens must carry `aud` (the app's game key): a token without it worked for every app sharing the secret.
- Manual grants are recorded within their app (`manual:<game_key>.<transaction_id>`): one app's server key could see whether another app used an id, or take it.
- Amazon notifications: the topic is checked before the signing certificate is fetched, an unpinned build keeps the first topic's confirmation and the setup check warns when a second topic sends signed messages (any AWS account can), and rejected notifications raise the alert like Google's and Apple's.
- Admin page: the token is kept for the tab only (no "Remember on this device"): every database of a SpacetimeDB host shares the page's address, so another database's page could read a token in localStorage.
- Dependency updates. In the module: `bytes` 1.12 (RUSTSEC-2026-0007), `anyhow`, `rand`, `keccak`, `spin`, `chrono`. In the native tests: `time`, `zstd` and others (since SpacetimeDB 2.16.3 the tests no longer build the host: `openssl`, `rustls`, `h2` and `rkyv` left the lockfile). The admin page: `recharts` 3.11, `lucide-react`, `vite` 8.3.8.
- The Audit workflow checks what ships, the module's wasm dependencies, with `cargo deny` (`server/deny.toml`; two accepted advisories in RSA and elliptic-curve signing, with the reasons). The whole lockfile, mostly the SpacetimeDB host the tests run on, is still listed by `cargo audit` for reference.

### Fixed

- The ledger worker no longer starves builds: it picked its batch from the 2000 oldest due rows, so a build with thousands of rows that keep failing took every run. Builds now take turns (at most 5 rows of a build, 25 in a run), read from an in-memory queue (`pending_purchase`), and an idle run reads no ledger row.
- `/restore` stops starting store checks after 15 seconds: the purchases it did not reach answer `503` in `results` (restore again) instead of holding the request for minutes.
- Requests without a player id (a paywall shown before sign-in) no longer share one player's rate limit: they get a bucket of the build sized for 50 players.
- The release archive `seed.example.zip` lacked `backup.py` (which `migrate.py` imports), `setup_google.py` and `mcp_server.py`.

### Changed

- `/entitlements`, `/restore` and the player profile read the purchases a player owns now (`owned_purchase`, in memory) instead of everything the player ever bought.
- Alerts, the setup check and the Overview read the worker's queue instead of every pending ledger row.
- Google Play subscription pause: a paused subscription is revoked in the game with reason `paused` (integration event `pause`, not churn), `/entitlements` lists it under `paused` with `resumes_at_ms`, the worker looks at it again when it should resume, and a resumed one is granted again (event `resume`).
- Apple Family Sharing: a shared purchase gives access (`family_shared` in `/entitlements`) and counts as no revenue.
- The store's offer wins over the client's: Apple `offerIdentifier` and `offerType` (`offer_type`: `intro`, `promo`, `code`, `winback`), Google offer or base plan id.
- Apple `REFUND_REVERSED` grants the purchase again (reason `reinstated`) and returns its revenue; a subscription period that ended meanwhile only gets its revenue back. The same applies to a won Stripe dispute.
- Xsolla partial refunds take the refunded amount out of revenue (they were ignored).
- `admin_reindex_ledger` (owner) rebuilds the two derived tables from the ledger; `backup.py restore` runs it, and the worker continues an unfinished rebuild.
- `/entitlements`, `/paywall`, `/paywall/event` and `/attributes` are one transaction each (the rate limit is checked in the route's own transaction); `/attributes` writes the player row only when something changed.
- A subscription's trial-conversion and paid-year facts are written with its ledger row (`trial_conversion`, `after_first_year`), so renewals, refunds and integration events no longer re-read the subscription's history. Integration events are not built for builds without integrations.
- Admin reads: the purchase list reads at most 20 000 ledger rows per call (its `next` cursor goes on from there), A/B results outside a test read the game's builds only, active-subscription counts read the owned purchases, `admin_select` reads a table without an index on the column once for all values. Retention, Steam order pruning and player erasure go through indexes.
- The admin page is embedded gzipped and served with `Content-Encoding: gzip`, an `ETag` and `Cache-Control: no-cache` (a repeated visit is a `304`): about 450 KB on the wire instead of 1.6 MB. The page uses the Latin subset of its font only, and the owner's reads of many ids are one `/sql` query per 50 ids. The wasm is stripped of its name section (5.2 MB → 3.5 MB).

**Upgrade:** not recorded (the changelog says it from 0.7.0 on).

### Security

- App Store notifications must be signed by Apple: the `signedPayload` JWS is verified (ES256, its `x5c` chain up to Apple Root CA - G3, which ships with the module, and Apple's marker extensions). Before, a build without `apple_notification_secret` accepted anything; the secret is now an optional extra check.
- Amazon SNS messages older than 6 hours are refused (replays), and a build can pin the SNS topic its notifications must come from (new `game_app.sns_topic_arn`, "SNS topic" on the Delivery tab; the setup check shows the topic last seen). Before, any AWS account could subscribe its own topic and replace the confirmation token.
- `/checkout/steam` checks the player's Web API auth ticket when the client sends one (`ticket`: hex of `GetAuthTicketForWebApi("purser")`, verified with `ISteamUserAuth/AuthenticateUserTicket`) and requires it when the build sets `require_ticket` (new `steam_build.require_ticket`, via `admin_set_steam_build`). Before, any client could start an order for any SteamID.
- Errors of outbound requests never contain the query string: GA4 `api_secret` and AppMetrica `post_api_key` could reach logs, `integration_health`, the setup check and alert messages on a timeout.
- Storing or deleting an alert channel's secret needs the secrets capability (Admin), not Configure (Editor).
- A Google RTDN refund only revokes purchases of the package that sent it.
- Google consume / acknowledge: the purchase state Google reports decides whether it is done; the error text only when the state cannot be read.
- Webhook integrations and alert channels accept only https URLs of public host names (no user info, IP address or local name). Xsolla `return_url` follows the Stripe rules (https; http only to localhost on sandbox builds).
- Request bodies are limited to 256 KiB; query parameters are percent-decoded.
- `admin_delete_credential` drops cached access tokens like `admin_set_credential`; `admin_grant_manual` validates the user and transaction ids and needs an enabled build.
- Google account binding compares user ids exactly (Apple tokens stay case-insensitive); a Google purchase without `purchaseState` grants nothing; path segments `.` / `..` are refused.
- The admin page is served with a CSP that allows only its own inline script (by hash, `admin/csp.txt` written by the build) instead of `'unsafe-inline'`; the demo build carries the same policy in a meta tag.
- Admin page: secret fields are masked, the setup wizard no longer overwrites the delivery token or webhook secret of a shared developer account, the sign-in token is kept after network errors, and CSV exports neutralize formula-like cells.
- Scripts: `seed.py --init` reads keys without echo and writes `credentials.json` with mode 0600 (now gitignored); `stdb.py` sends the token only over https or to localhost and drops it on cross-host redirects; `migrate.py` takes `PURSER_FROM_TOKEN` for a source server on another host; the MCP server answers malformed requests with errors instead of exiting.
- CI and release: checkouts no longer keep the token, the release builds without write access and publishes in a separate job, third-party actions are pinned by commit, and the personal-names check reads its pattern from the `PRIVATE_NAMES_RE` repository variable.

### Changed

- Outbound work is limited by time instead of by counts sized for the old 500 ms cap: a client request starts store and delivery calls for at most 5 s (`ctx::REQUEST_BUDGET_SECS`) and leaves the rest to the worker; a worker run starts calls for at most 40 s (`ctx::WORKER_BUDGET_SECS`). A slow store can no longer hold a run for minutes.
- New error code `[ERR_ALERT_SECRET_MISSING]` when an alert channel is enabled without its secret (was `[ERR_BAD_ALERT]`).
- Internal cleanup: shared HTTP plumbing in the module (`web.rs`), one implementation of percent-encoding, Basic auth and constant-time comparison (`purser_core::encoding`), amounts (`purser_core::money`, with overflow checks), dates, UUIDs and X.509 / DER (`purser_core::x509`); `Purchase::new`; dead code and stale comments removed.

**Upgrade:** a first install; databases of earlier builds need a publish with `--delete-data`.

Needs an App Store Connect API Team key (new optional account secrets `apple_connect_key_id`, `apple_connect_private_key_p8`; the issuer id is shared). Only for players who consented in the game (`attribution.refund_data_consent`, `SetRefundDataConsent` in the Unity package). Answers are queued in `apple_consumption_outbox`, retried until the deadline and listed in the purchase history; the setup check shows the mode.
- Integration health: for every build and integration the module keeps the last sent event, the last failure (retried or dropped, with the error) and the last event skipped because the client did not send the device id the integration needs (`integration_health`). The Integrations tab shows it under each build, and the setup check reports failures and missing device ids instead of only checking the settings.
